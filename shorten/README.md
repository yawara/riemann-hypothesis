# 証明の短縮

検証(このリポジトリの本来の目的)のあとに取り組む、2 つ目の目標です。配布された Lean 証明
(**175,187 ファイル・17,374,215 行・約 1.03 GB**)を、主張を変えずにどこまで短くできるかを調べます。
2026-11-22 に始めました。

## 守ること

- 主張は変えない。`Statements.lean`(検証者の命題と一致することを確かめたもの)と、`Main.lean` の主定理 5 件はそのまま残す。
  短くした版にも、検証と同じ検査(ビルド、`#print axioms`、主張の一致、カーネル再検査)をかける。
- 原本 `evidence/` と、検証に使っている `lean/` は書き換えない。短縮版は別の場所に写して作る
  (`lean/` のソースは、検証の最後のソース不変確認の対象)。
- 配布物にも PDF にもライセンスの表示がないため、短縮版のソースそのものは公開しない。公開するのは、
  短縮の手順(スクリプト)、消した宣言やまとめた宣言の一覧、規模の数字。
- 検証の常駐プロセスが動いているあいだは、重い処理を `nice` で優先度を下げて走らせる。

## 段階

1. 機械的な短縮
   1. 使われていないものを消す。主定理の証明項から辿れない宣言と、そういう宣言しか入っていないモジュール。
   2. 明らかな重複をまとめる。型が同じ定理、型も値も同じ定義、別の定理をそのまま返すだけの定理(別名)。
   3. Mathlib にあるものを置き換える。Mathlib(と Lean 本体・Batteries)に同じ型の定理があるもの。
2. 数学的な短絡。証明の筋道そのものに近道がないかを探す。1. で残った骨格を読んで考える。

段ごとに短縮版をビルドし直し、検査を通してから次の段へ進みます。

## 規模の測り方

README の「Lean コードの規模」と同じ数え方(`.lean` のファイル数・行数・バイト数)に宣言の数を加えて、
段ごとの減り方を記録します。

## 下調べ: どの宣言が実際に使われているか

`scripts/shorten_analyze.sh` が、Lean で書いた解析ツール [`tools/rhshrink`](tools/rhshrink/Main.lean) で次を調べます。
配布物のビルド結果(`.olean`)を読み込むだけなので、検証と並行して走らせられます。

- 主定理 5 件から、型と値(証明項)に現れる定数を推移的に辿る。配布物の各宣言を、次の 3 つに分ける。
  - `live`: 宣言の定数そのものが使われている
  - `aux`: 宣言そのものは使われていないが、その補助定数(`foo.match_1` など)だけが別の宣言から使われている
  - `dead`: 使われていない
- Lean がビルド結果に残している宣言の位置(行範囲)から、使われていない行数をモジュールごとに数える。
- 使われている定理のうち、型が同じものの組(重複)、外部(Mathlib など)に同じ型の定理があるもの、別名を挙げる。
  型は、宇宙レベルとメタデータを消してから α 同値で比べる。

これはカーネルの項の上での解析です。エラボレーションのときにだけ使われるもの(notation、マクロ、
証明項に痕跡を残さない `dsimp` 用の rfl 補題など)は数えていません。「使われていない」と出た宣言を
本当に消せるかは、消したソースをビルドし直して確かめます。

出力(`/var/tmp/riemann-hypothesis-ywr/runs/shorten/analysis-<時刻>/`)

| ファイル | 中身 |
|---|---|
| `summary.json` | 集計 |
| `modules.tsv` | モジュールごとの定数・宣言の数と、live / aux / dead の行数 |
| `decls.tsv.zst` | 宣言ごとの行範囲と状態 |
| `reachable.txt.zst` | 証明から到達できる、配布物の定数の一覧 |

**残す宣言の決め方**

2. ソースの辺: 残す宣言のソースが参照する宣言(`.ilean`。`simp [X]` で結局使われなかった `X` や、失敗した分岐の中の名前など、

さらに、証明項にも参照にも跡を残さずにエラボレーションで使われうる宣言(22,043 個)は、使われていなくても残し、
閉包の起点に加えた(`scripts/shorten_protect.py`)。

### 次の手順

1. 短縮版全体のビルドを通す。失敗があれば規則を直して作り直し、続きからビルドする。通ったら、検証と同じ検査
   (主定理の公理、主張の一致、カーネル再検査)を短縮版にかける。
2. 解析の裏取り: nanoda のために書き出している主定理の依存一式(lean4export)の定数の集合と、
   rhshrink の到達可能な定数の集合を突き合わせる。
3. 段階 1b(重複の統合): 型が同じ定理の写し(99,393 個)と別名(51,527 個)を、参照を書き換えてまとめる。

### 次の短縮の道(2026-11-24 の見積もり)

段階 1a の短縮版(14,160,262 行)に対する見込み。行は宣言の行範囲で数えたもので、モジュールごと消えれば import などの行も減る。

| 道 | 規模 | 中身 | 作り直しの範囲 |
|---|---:|---|---|
| 同じ主張の定理の重複(本体どうし) | 62,415 個・約 39 万行 | 同じ補題を何度も証明している(最大の組では 193 回)。1 つを残して参照を書き換える | 参照しているモジュールと、その直接の利用者 |
| `…Statement` の包み | 37,786 モジュール・435,331 行(バイトでは 6.7%) | 主張を書き直し、`first \| exact @X \| …` で別の定理 X を返すだけ。参照を X に書き換えてモジュールごと消す | 同上 |
| 守る宣言の見直し | 最大で約 23 万行 | カーネルの項で使われないのに残している宣言(約 4.5 万個)。大半は、使われていない instance・simp 補題・記法の証明が使う宣言。rfl でない simp 補題や、強制変換でない instance は、使われれば証明項に跡が残るので消せる見込みが高い | 試しのビルドで確かめながら |
| Lean が指摘する無駄 | 約 12 万か所(行はほぼ減らない) | 実行されない分岐 9.4 万、何もしないタクティク 9.6 万(多くは同じ箇所)、使われない simp の引数 2.4 万(2 回目の全体ビルドのログ)。前の 2 つの 8 割は `…Statement` の包みの中 | 包みを消せば大半は消える |
| Mathlib への置き換え(段階 1c) | 215 個・840 行(字面どおり一致するもの) | 型の書き方の違いを越えて探すには `exact?` などが要り、重い | 小さい |

行数は書式にも左右される(空行 10.6%、import 4.7% など)。空行を詰めるような見かけの短縮は数えない。
名前が使われていない `have` を消す道も調べたが、Lean の警告(約 2.4 万)のほとんどは定理の引数の仮定で、行は減らない。

作り直しを最小にするため、書き出しは決定的にして、変わらないファイルをバイト単位で同じに保つ。書き出したら今の短縮版との差を取り、
変わるモジュールとその下流の数(= 作り直す数。Lake は下流をすべて作り直す)を先に確かめる。危なそうなモジュールは今の環境で
単体コンパイルしてから全体をビルドする。下流の多いモジュール(import の階層の下のほう)を変えると作り直しが大きくなるので、
段階 1b はまず一部の組で試しにビルドして失敗の型を集め、残りはまとめて 1 回で書き換える(何度かに分けると、そのたびに下流を作り直す)。
