# 証明の短縮

検証(このリポジトリの本来の目的)のあとに取り組む、2 つ目の目標です。配布された Lean 証明
(**175,187 ファイル・17,374,215 行・約 1.03 GB**)を、主張を変えずにどこまで短くできるかを調べます。
2026-11-22 に始めました。

## 守ること

- 主張は変えない。`Statements.lean`(検証者の命題と一致することを確かめたもの)と、`Main.lean` の主定理 5 件はそのまま残す。
  短くした版にも、検証と同じ検査(ビルド、`#print axioms`、主張の一致、カーネル再検査)をかける。
- 原本 `evidence/` と、検証に使っている `lean/` は書き換えない。短縮版は別の場所に写して作る
  (`lean/` のソースは、検証の最後のソース不変確認の対象)。
- 配布物にも PDF にもライセンスの表示がないため、短縮版のソースそのものは公開しない。公開するのは、
  短縮の手順(スクリプト)、消した宣言やまとめた宣言の一覧、規模の数字。
- 検証の常駐プロセスが動いているあいだは、重い処理を `nice` で優先度を下げて走らせる。

## 段階

1. 機械的な短縮
   1. 使われていないものを消す。主定理の証明項から辿れない宣言と、そういう宣言しか入っていないモジュール。
   2. 明らかな重複をまとめる。型が同じ定理、型も値も同じ定義、別の定理をそのまま返すだけの定理(別名)。
   3. Mathlib にあるものを置き換える。Mathlib(と Lean 本体・Batteries)に同じ型の定理があるもの。
2. 数学的な短絡。証明の筋道そのものに近道がないかを探す。1. で残った骨格を読んで考える。

段ごとに短縮版をビルドし直し、検査を通してから次の段へ進みます。

## 規模の測り方

README の「Lean コードの規模」と同じ数え方(`.lean` のファイル数・行数・バイト数)に宣言の数を加えて、
段ごとの減り方を記録します。

## 下調べ: どの宣言が実際に使われているか

`scripts/shorten_analyze.sh` が、Lean で書いた解析ツール [`tools/rhshrink`](tools/rhshrink/Main.lean) で次を調べます。
配布物のビルド結果(`.olean`)を読み込むだけなので、検証と並行して走らせられます。

- 主定理 5 件から、型と値(証明項)に現れる定数を推移的に辿る。配布物の各宣言を、次の 3 つに分ける。
  - `live`: 宣言の定数そのものが使われている
  - `aux`: 宣言そのものは使われていないが、その補助定数(`foo.match_1` など)だけが別の宣言から使われている
  - `dead`: 使われていない
- Lean がビルド結果に残している宣言の位置(行範囲)から、使われていない行数をモジュールごとに数える。
- 使われている定理のうち、型が同じものの組(重複)、外部(Mathlib など)に同じ型の定理があるもの、別名を挙げる。
  型は、宇宙レベルとメタデータを消してから α 同値で比べる。

これはカーネルの項の上での解析です。エラボレーションのときにだけ使われるもの(notation、マクロ、
証明項に痕跡を残さない `dsimp` 用の rfl 補題など)は数えていません。「使われていない」と出た宣言を
本当に消せるかは、消したソースをビルドし直して確かめます。

出力(`/var/tmp/riemann-hypothesis-ywr/runs/shorten/analysis-<時刻>/`)

| ファイル | 中身 |
|---|---|
| `summary.json` | 集計 |
| `modules.tsv` | モジュールごとの定数・宣言の数と、live / aux / dead の行数 |
| `decls.tsv.zst` | 宣言ごとの行範囲と状態 |
| `reachable.txt.zst` | 証明から到達できる、配布物の定数の一覧 |
| `external-used.tsv` | 配布物の証明が直接使っている外部の定数 |

| `aliases.tsv` | 値が「定数を適用しただけ」の定理・定義(`non_bvar_args` が 0 なら純粋な別名) |

## 結果

### 下調べ(2026-11-22。解析 14 分 44 秒、最大メモリ 101 GiB)

記録は [`results/01-analysis/`](results/01-analysis/)(`summary.txt` が要約)。

**配布物の全体**: 175,187 モジュール、**17,374,215 行**、1,030,531,854 バイト。宣言 1,147,761 個(定数 1,945,519 個)。

**主定理 5 件の証明が使っているもの**: 配布物の定数 1,265,279 個(65.0%)、宣言 854,438 個(74.4%)。
外部(Mathlib など)の定数は直接 67,981 個を使う。

**段階 1a(使われていないものを消す)の見込み**

| | モジュール | 行 | バイト |
|---|---:|---:|---:|
| 使われている宣言を 1 つも持たないモジュール | 28,709 | 2,374,770(13.7%) | 143,376,453 |
| 使われているモジュールの中の、使われていない宣言 | − | 924,745(5.3%) | − |
| 合計 | | **3,299,515(19.0%)** | |

**段階 1b(重複)の見込み**

- 型が同じ定理: 70,445 組。余分な写しが 99,393 個、行範囲の合計で約 49 万行。最も大きい組では、
  同じ補題(スキームの射の合成についての等式)が 193 回証明されている。
- 型も値も同じ定義: 2,689 組。余分な写しが 4,306 個、約 7,500 行。
- 別名(値が別の定数をそのまま返すだけの定理・定義): 51,527 個。うち 47,268 個は上の重複の組に入る。
  多くは名前が `…Statement` で終わるモジュールにある主張の写しで、使われている `…Statement` モジュールは
  37,306 個・504,098 行ある。

**段階 1c(Mathlib)の見込み**

型が字面どおり一致する定理は 215 個(840 行)だけだった。例: `primesLE_eq_filter_prime_range` と
`Nat.primesLE_eq_filter_range`。型の書き方の違い(インスタンスの形、引数の順序など)を越えて探す方法が要る。

**ソースの行の内訳**: 宣言など 77.0%、空行 10.6%、`import` 5.2%、`namespace`・`section`・`end` 3.0%、
`open` 2.9%、`variable` 0.8%、`set_option` 0.5%。コメントはほとんどない。

**読み方の注意**

- カーネルの項の上での見込みです。配布物には局所的な notation が 1,695 か所、マクロが 64 個などあり、
  証明項に残らない参照(`simp [X]` で結局使われなかった `X` など)もあるので、実際に消せるかは再ビルドで確かめます。
- 行数は書式に左右されます(空行だけで 10.6%)。書式に左右されない尺度として、宣言の数と、
  カーネルに渡る証明項の大きさ(lean4export の出力)も併せて記録します。

### 次の手順

1. 解析の裏取り: nanoda のために書き出している主定理の依存一式(lean4export)の定数の集合と、
   rhshrink の到達可能な定数の集合を突き合わせる。
2. 段階 1a の短縮版を作る: `lean/` を別の場所に写し、使われていないモジュールを消して import をつなぎ直し
   (消したモジュールの import を引き継ぐ)、使われていない宣言の行を消す。ソースの字面で名前が参照されている
   宣言は、最初の版では残す。
3. 短縮版をビルドする。全体のビルドは 20 時間規模なので、検証の常駐プロセス(nanoda、Mathlib の再ビルド照合)が
   CPU を使い終えてから始める。
