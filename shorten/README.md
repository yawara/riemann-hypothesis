# 証明の短縮

検証(このリポジトリの本来の目的)のあとに取り組む、2 つ目の目標です。配布された Lean 証明
(**175,187 ファイル・17,374,215 行・約 1.03 GB**)を、主張を変えずにどこまで短くできるかを調べます。
2026-11-22 に始めました。

## 守ること

- 主張は変えない。`Statements.lean`(検証者の命題と一致することを確かめたもの)と、`Main.lean` の主定理 5 件はそのまま残す。
  短くした版にも、検証と同じ検査(ビルド、`#print axioms`、主張の一致、カーネル再検査)をかける。
- 原本 `evidence/` と、検証に使っている `lean/` は書き換えない。短縮版は別の場所に写して作る
  (`lean/` のソースは、検証の最後のソース不変確認の対象)。
- 配布物にも PDF にもライセンスの表示がないため、短縮版のソースそのものは公開しない。公開するのは、
  短縮の手順(スクリプト)、消した宣言やまとめた宣言の一覧、規模の数字。
- 検証の常駐プロセスが動いているあいだは、重い処理を `nice` で優先度を下げて走らせる。

## 段階

1. 機械的な短縮
   1. 使われていないものを消す。主定理の証明項から辿れない宣言と、そういう宣言しか入っていないモジュール。
   2. 明らかな重複をまとめる。型が同じ定理、型も値も同じ定義、別の定理をそのまま返すだけの定理(別名)。
   3. Mathlib にあるものを置き換える。Mathlib(と Lean 本体・Batteries)に同じ型の定理があるもの。
2. 数学的な短絡。証明の筋道そのものに近道がないかを探す。1. で残った骨格を読んで考える。

段ごとに短縮版をビルドし直し、検査を通してから次の段へ進みます。

## 規模の測り方

README の「Lean コードの規模」と同じ数え方(`.lean` のファイル数・行数・バイト数)に宣言の数を加えて、
段ごとの減り方を記録します。

## 下調べ: どの宣言が実際に使われているか

`scripts/shorten_analyze.sh` が、Lean で書いた解析ツール [`tools/rhshrink`](tools/rhshrink/Main.lean) で次を調べます。
配布物のビルド結果(`.olean`)を読み込むだけなので、検証と並行して走らせられます。

- 主定理 5 件から、型と値(証明項)に現れる定数を推移的に辿る。配布物の各宣言を、次の 3 つに分ける。
  - `live`: 宣言の定数そのものが使われている
  - `aux`: 宣言そのものは使われていないが、その補助定数(`foo.match_1` など)だけが別の宣言から使われている
  - `dead`: 使われていない
- Lean がビルド結果に残している宣言の位置(行範囲)から、使われていない行数をモジュールごとに数える。
- 使われている定理のうち、型が同じものの組(重複)、外部(Mathlib など)に同じ型の定理があるもの、別名を挙げる。
  型は、宇宙レベルとメタデータを消してから α 同値で比べる。

これはカーネルの項の上での解析です。エラボレーションのときにだけ使われるもの(notation、マクロ、
証明項に痕跡を残さない `dsimp` 用の rfl 補題など)は数えていません。「使われていない」と出た宣言を
本当に消せるかは、消したソースをビルドし直して確かめます。

出力(`/var/tmp/riemann-hypothesis-ywr/runs/shorten/analysis-<時刻>/`)

| ファイル | 中身 |
|---|---|
| `summary.json` | 集計 |
| `modules.tsv` | モジュールごとの定数・宣言の数と、live / aux / dead の行数 |
| `decls.tsv.zst` | 宣言ごとの行範囲と状態 |
| `reachable.txt.zst` | 証明から到達できる、配布物の定数の一覧 |
| `external-used.tsv` | 配布物の証明が直接使っている外部の定数 |
| `duplicates.tsv` | 型が同じ定理の組と、型も値も同じ定義の組 |
| `external-matches.tsv` | 外部に同じ型の定理がある、配布物の定理 |
| `aliases.tsv` | 値が「定数を適用しただけ」の定理・定義(`non_bvar_args` が 0 なら純粋な別名) |

### 段階 1a: 使われていない宣言を消す(2026-11-22。短縮版を作成、全体のビルドで確認中)

記録は [`results/02-stage1a/`](results/02-stage1a/)。短縮版のソースは `/var/tmp/riemann-hypothesis-ywr/shorten/stage-1a/`
(公開しない。手順は下の通りで、スクリプトを原本に当てれば作り直せる)。

| | 元 | 段階 1a | 差 |
|---|---:|---:|---:|
| モジュール | 175,187 | 148,924 | −15.0% |
| **行** | **17,374,215** | **14,159,480** | **−18.5%** |
| 空行を除く行 | 15,531,759 | 12,649,387 | −18.6% |
| バイト | 1,030,531,854 | 832,996,984 | −19.2% |
| 宣言 | 1,147,761 | 899,791 | −21.6% |

**残す宣言の決め方**

「カーネルの項で使われる」だけでは足りなかった。次の 3 つで閉包をとり、増えなくなるまで交互に繰り返した
(`results/02-stage1a/closure-iterations.tsv`)。

1. カーネルの辺: 残す宣言の型と証明項に現れる定数(rhshrink)。
2. ソースの辺: 残す宣言のソースが参照する宣言(`.ilean`。`simp [X]` で結局使われなかった `X` や、失敗した分岐の中の名前など、
   証明項に跡を残さない参照を含む)。宣言の外(`variable`・`attribute`・`open (…)` など)からの参照も、
   そのモジュールに残す宣言があれば辿る。
3. マクロの辺: マクロ(`macro`・`elab`、91 個)の本文に書かれた名前。構文の引用の中の名前は、マクロを定義した位置で解決され、
   展開した先の参照は `.ilean` に残らない(`simp only [X]` の X が rfl の補題なら証明項にも残らない)。そこで、本文の識別子を
   定義の位置の名前空間と `open` を踏まえて宣言に解決し(251 個)、マクロのキーワードが現れる宣言(1,381 か所)からの参照とみなした
   (`results/02-stage1a/macro-refs.tsv`・`macro-uses.tsv.zst`)。名前の末尾だけで照合すると `e`・`h`・`mk` などが大量に当たり、
   942 個も足してしまったので、この形にした。

さらに、証明項にも参照にも跡を残さずにエラボレーションで使われうる宣言(22,043 個)は、使われていなくても残し、
閉包の起点に加えた(`scripts/shorten_protect.py`)。

- notation・マクロなどのメタ命令(生成される構文の定数が宣言の行範囲を持つ)
- instance(強制変換の instance は展開されて証明項に残らない)
- `@[simp]` の補題(rfl の補題は dsimp が跡を残さずに使う)
- 別名の定数を生成する属性(`@[reassoc]`・`@[simps]`・`@[to_additive]` など)と、タクティクの拡張に登録する属性

閉包は 6 回で閉じ、残す宣言は 899,791 個になった(カーネルの項だけなら 854,438 個)。マクロの辺で足したのは 6 個
(`nabA_eq` など、1〜2 行の補題)で、それらの証明項が新たに使う宣言は無かった。

**ソースの書き換え**(`scripts/shorten_stage1a.py`)

- 残さない宣言(247,970 個)と `example`・`#check` を消し、それに掛かる `… in` の前置き(`set_option`・`open`・`omit`・`include`・
  `variable`・`attribute […]`・`unseal`・`universe`。複数行のもの、空行を挟むもの、連なったものを含む)も消す。
- 残す宣言が無くなった 26,263 モジュールを消す。消したモジュールを import していたモジュールは、その import を引き継いで推移簡約する
  (import の閉包は変わらない)。
- `attribute`・`open X (…)`・`export X (…)` からは、消す宣言を指す名前を外す(位置は `.ilean` の参照で特定。字下げで続く行も含む)。
- その位置から見えなくなる名前空間は `open` から外す(1,526 か所、12 行を削除)。見えるかどうかは、import の閉包に残る宣言と
  `namespace` 命令に加えて、同じモジュールでは `open` より前にあるものだけで判定する(Lean は `open` の時点で名前空間があるかを確かめる)。
  同じモジュールの後ろで初めて現れ、名前空間の外から短い名前で参照される 3 か所は、`open` に残し、その前に
  `namespace X end X` の 1 行を入れて名前空間を作る(外すと参照が解決できなくなるため)。
- 消した宣言の前後で続いた空行は 1 行にまとめる。

**確認**

依存の少ない 40 モジュール(依存を含めて約 360 モジュール)を 3 回試しにビルドし、失敗(17 → 4 → 0)の原因を
上の規則に取り込んだ(`results/02-stage1a/test-builds.txt`)。

2026-11-22 20:26 から短縮版全体のビルドを検証と並行して低い優先度で実行し、23:16 に 26,775 モジュールが通った時点で止めた。
失敗した 30 モジュールの原因(`results/02-stage1a/full-build1-failures.tsv`)は次の 5 つで、すべて上の規則に取り込んだ。

| 原因 | モジュール |
|---|---:|
| 消した宣言に掛かっていた `attribute … in`・`universe … in` の前置きが残り、後ろの `end` などに掛かった | 16 |
| 同じモジュールの後ろで初めて現れる名前空間を、`open` の位置で見えるとみなした | 5 |
| `export X (…)` の名前の並びから、消した宣言を外していなかった | 4 |
| `open` の字下げで続く行にある、見えなくなった名前空間を外していなかった | 4 |
| マクロの本文が参照する rfl の補題を消した | 1 |

書き出し直した短縮版(変わったのは 222 モジュール)で、23:21 から続きのビルドをしている。Lake は import 先の `.olean` の中身の
ハッシュで作り直すかを決めるので、作り直しになるのは変わったモジュールとその下流だけ(そのうちビルド済みだったのは 775 個)。

### 次の手順

1. 短縮版全体のビルドを通す。失敗があれば規則を直して作り直し、続きからビルドする。通ったら、検証と同じ検査
   (主定理の公理、主張の一致、カーネル再検査)を短縮版にかける。
2. 解析の裏取り: nanoda のために書き出している主定理の依存一式(lean4export)の定数の集合と、
   rhshrink の到達可能な定数の集合を突き合わせる。
3. 段階 1b(重複の統合): 型が同じ定理の写し(99,393 個)と別名(51,527 個)を、参照を書き換えてまとめる。
