速度は観測のたびに少しずつ落ちていきました。第 1 回は 1 分あたり 221 モジュール、第 10 回から第 26 回までは 100〜130 の間でした。計算機の不調ではありません。ビルドの途中(11/21 21:10 JST ごろ)に 22 秒間測ったところ、CPU は 128 スレッドのうち 79 本ぶんしか使っておらず、メモリとディスクにも余裕がありました(表 2)。Lean のコンパイル自体も速いままでした。計測のあいだに動いていた lean プロセスは、起動からの経過時間が中央値 7 秒、90% 点でも 17 秒でした。

時間を使っていたのは、ビルドツール Lake の準備です。同じ計測で、Lake 本体が CPU を 35 本ぶん使っていました。Lake は 1 モジュールをコンパイルする前に、そのモジュールが推移的に import するモジュールを、毎回最初から 1 つずつたどって、成果物の一覧を作ります(Lake の fetchTransImportArts。7.3 節の注に書いた setup.json の中身です)。たどる数は、Mathlib など外部の約 8,700 個に、プロジェクト内の import を足した数です。配布物の Lean ファイルは module 宣言を 1 つも使っていないので(0 / 175,187)、一覧には import 先の成果物がすべて入ります。

66 主定理として何が主張されているか

リーマン予想は、ζ 関数の自明でない零点がすべて直線 Re⁡s=12\operatorname{Re} s = \tfrac12Res=21​ の上にある、という主張です(図 1)。配布物は、これを Lean の定理として次のように述べています。

最終的な主張は、配布物の Main.lean にある 5 つの定理です。そのうち 4 つの命題は Statements.lean で定義されています。この Statements.lean は import Mathlib だけを行うファイルで、プロジェクト側の定義を一切使っていません。

表 85 つの主定理。

定理名主張の内容
riemannHypothesisMathlib が定義する RiemannHypothesis そのもの。ζ(s) = 0 で、s が自明な零点(−2, −4, …)でも 1 でもなければ Re s = 1/2。
riemannZeta_eq_zero_re同じ主張を、Mathlib の定義名を使わずに書き下したもの。
LFunction_ne_zero_of_half_lt_re一般化リーマン予想(半平面形)。任意の法 N の Dirichlet 指標 χ について、Re s > 1/2 なら L(s, χ) ≠ 0。
LFunction_eq_zero_re一般化リーマン予想(臨界帯形)。0 < Re s < 1 にある L(s, χ) の零点は Re s = 1/2 上にある。
LFunction_eq_zero_re_of_isPrimitive上と同じ主張を原始指標に限ったもの。

def RiemannHypothesis : Prop :=

  (_ : ¬∃ n : ℕ, s = -2 * (n + 1))
  (_ : s ≠ 1),
  s.re = 1 / 2
Mathlib/NumberTheory/LSeries/RiemannZeta.lean より。改行の位置は余白の幅に合わせて変えています。

主張の書き方そのものは、Mathlib の既存の定義(riemannZeta、DirichletCharacter.LFunction)に対する標準的な定式化です。主定理の直前の数ファイル(関数等式で左半分を右半分に移す議論など)は目で読み、Mathlib の定理を使った通常の議論であることを確認しました。膨大な本体部分は読んでおらず、そこは Lean のカーネルによる検査に委ねます。

7.4主定理が依存する公理標準の 3 公理のみ

標準の 3 公理propext 同値な命題は等しい。Classical.choice 空でない型から要素を 1 つ選べる(選択公理)。Quot.sound 関係のある 2 つの元は、商では等しい。

5 つの主定理それぞれについて #print axioms を実行しました。Lean 4 と Mathlib の標準は propext・Classical.choice・Quot.sound の 3 つです。これ以外(sorryAx や独自公理)が現れた場合、その定理は無条件に証明されたとは言えません。結果は、5 つとも標準の 3 つだけでした。

この表示は、コンパイルで作られた環境に記録されている証明をたどった結果です。その環境がカーネルの検査を正しく通って作られたことは、7.6 節の再検査と 7.7 節の照合で、別に確かめます。

7.5主張の一致確認一致

7.6カーネルによる再検査実行中

ツールチェーン同梱の leanchecker で、全モジュールの宣言をカーネルに再生させます。エラボレータやメタプログラムを経由しない検査なので、カーネルを迂回して環境に宣言を押し込む細工があれば検出できます。公式キャッシュから取得した Mathlib 側のモジュールも同じ方法で再検査します。

1 回目は 2026-11-22 9:22 JST に、ツールチェーン同梱の leanchecker をそのまま使って始めました。ところが leanchecker は、引数に渡したモジュール名 1 つごとに、検索パス上の約 18.6 万個の .olean をすべて走査し直して、名前に当てはまるモジュールを探します。1 回の走査に 100 並列で約 6.5 分かかり、名前を探すだけで約 8 日かかる見込みになったため、1 時間 43 分で止めました。止めた時点では、まだどのモジュールの再生も始まっていませんでした。

そこで、leanchecker の再生の処理(replayFromImports)を一字一句そのまま写し、名前を探す部分だけを省いた小さなプログラムrhcheckを作りました。モジュール名を直接渡すので、探す手間がかかりません。再生の中身は leanchecker と同じで、各モジュールの宣言を、そのモジュールの import だけを読み込んだ環境へ、カーネルを通して 1 つずつ追加し直します。本番の前に、主定理の直前のモジュール Supplements.Kernels.MainTheoremsAll を含む 3 つのモジュールを、公式の leanchecker と rhcheck の両方で再生し、どちらも通ることを確かめました。

2 回目は 11:26 JST に始め、175,187 モジュールを 100 並列で再生しています。進み具合は巻頭と 2 節の表 2 に出しています。

99 この検証で言えること、言えないこと

すべての検査が通った場合に言えること

配布された Lean ソースが、指定どおりの Lean 4.33.1 と Mathlib v4.33.1 のもとでエラーなくコンパイルでき、主定理が標準の 3 公理だけに依存している、ということです。Lean のカーネルが正しく、Mathlib の riemannZeta などの定義が意図どおりである限り、これは Mathlib の RiemannHypothesis が証明されたことを意味します。

言えないこと

  • 証明の数学的な筋道が正しく理解できるか、既知の障害をどう越えているかは、この検証の対象外です。1,700 万行を人間が読んだわけではありません。
  • Lean のカーネル実装そのものの正しさは前提としています。別実装のカーネル(nanoda)による照合は準備済みですが、この時点ではまだ行っていません。
  • Mathlib 本体は公式のビルド済みキャッシュを使っています。ソースから再ビルドしてキャッシュと突き合わせる照合は、全検査の最後に予定しています。
  • 検証は 1 台の計算機、1 回の実行によるものです。
  • 配布元と著者については、PDF とサーバ応答から分かる範囲しか確認していません。
