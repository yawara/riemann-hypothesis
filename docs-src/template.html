§4

主定理として何が主張されているか

最終的な主張は、配布物の Main.lean にある 5 つの定理です。そのうち 4 つの命題は Statements.lean で定義されています。この Statements.lean は import Mathlib だけを行うファイルで、プロジェクト側の定義を一切使っていません。

定理名主張の内容
riemannHypothesisMathlib が定義する RiemannHypothesis そのもの。ζ(s) = 0 で、s が自明な零点(−2, −4, …)でも 1 でもなければ Re s = 1/2。
riemannZeta_eq_zero_re同じ主張を、Mathlib の定義名を使わずに書き下したもの。
LFunction_ne_zero_of_half_lt_re一般化リーマン予想(半平面形)。任意の法 N の Dirichlet 指標 χ について、Re s > 1/2 なら L(s, χ) ≠ 0。
LFunction_eq_zero_re一般化リーマン予想(臨界帯形)。0 < Re s < 1 にある L(s, χ) の零点は Re s = 1/2 上にある。
LFunction_eq_zero_re_of_isPrimitive上と同じ主張を原始指標に限ったもの。

主張の書き方そのものは、Mathlib の既存の定義(riemannZeta、DirichletCharacter.LFunction)に対する標準的な定式化です。主定理の直前の数ファイル(関数等式で左半分を右半分に移す議論など)は目で読み、Mathlib の定理を使った通常の議論であることを確認しました。膨大な本体部分は読んでおらず、そこは Lean のカーネルによる検査に委ねます。

Lean を動かす前に、全ソース(1.03 GB)を文字列検索しました。「証明済み」に見せかける抜け道になりうる記述と、ビルド時に任意のコードを実行しうる記述を数えています。

メタプログラムを含むファイルは人間が読んで確認しました。CutCptCopy.lean は既存の定義・定理を、名前を付け替えて addDecl で登録し直すコマンドを定義しています。addDecl は通常どおりカーネル検査を経由するので、これ自体は健全性を損ないません。OwnStruct.lean と HeckeNonvanishing/Imports.lean は、項を組み立ててゴールに割り当てるタクティク(kcopy、kexactB)で、最終的な型の一致はカーネルが判定します。いずれも、後述のカーネル再検査の対象です。

静的スキャンは補助的な検査です。文字列検索をすり抜ける細工の可能性は残るため、最終判断はカーネルによる検査で行います。全項目の結果は verification/static-scan/ にあります。

5.2依存ライブラリの真正性 完了

配布物が固定している Mathlib のコミット 0df444a360eaa60ab8c11dca51a86af692955474 は、公式リポジトリ leanprover-community/mathlib4 のタグ v4.33.1 と一致しました。master ブランチとの差は lean-toolchain の 1 行だけです。Batteries や Aesop など他の 8 つの依存も、Mathlib 自身が固定している版と完全に一致します。改変された Mathlib を掴まされている、という可能性はありません。

5.3全モジュールのコンパイル 進行中

配布物の lakefile.toml・lake-manifest.json・lean-toolchain をそのまま使い、ソースに一切手を加えずに lake build を実行しています。Mathlib は公式のビルド済みキャッシュを取得して利用しました。

注意ビルド手順に加えた工夫が 1 つあります。Lake 5 はモジュールごとに、推移的に import する全成果物のパスを列挙した setup.json を書き出します。import Mathlib だけで約 6 MB あり、このプロジェクト全体では合計 1.4 TB を超える見積もりになって検証機のディスクに収まりません。そこで、ビルド済みモジュールの setup.json を随時削除するスクリプトを並走させています。このファイルは Lean 起動時の入力にすぎず、削除しても再ビルドが起きないこと(成果物として追跡されていないこと)を事前に小さな例で確認しました。ソース・設定・コンパイラには触れていません。

5.4主定理が依存する公理 未実施

ビルド完了後、5 つの主定理それぞれについて #print axioms を実行します。Lean 4 と Mathlib の標準は propext・Classical.choice・Quot.sound の 3 つです。これ以外(sorryAx や独自公理)が現れた場合、その定理は無条件に証明されたとは言えません。

5.5主張の一致確認 未実施

検証者が Mathlib だけを import して書いた命題(RHReference.lean)を、配布物の主定理でそのまま証明できるかをカーネルに判定させます。あわせて、主定理の型に現れる定数を定義の中身まで推移的に辿り、主張がプロジェクト側の定義に依存していないことを機械的に確認します。

5.6カーネルによる再検査 未実施

ツールチェーン同梱の leanchecker で、全モジュールの宣言をカーネルに再生させます。エラボレータやメタプログラムを経由しない検査なので、カーネルを迂回して環境に宣言を押し込む細工があれば検出できます。公式キャッシュから取得した Mathlib 側のモジュールも同じ方法で再検査します。

5.7別実装のカーネルによる照合 未実施

ここまでの検査はすべて Lean 本体のカーネル(C++ 実装)に依存します。カーネル自体の不具合を突かれている可能性を減らすため、主定理 5 件が推移的に依存する定義・定理・公理をすべて lean4export で書き出し、Rust で書かれた別実装の型検査器 nanoda に検査させます。許可する公理は標準の 3 つだけです。

準備として、主張の定義 RiemannZetaZerosOnLine(Mathlib のみに依存)の依存一式を書き出して検査し、53,240 宣言がエラーなく通ることを確認しました。使用した版は lean4export v4.33.0、nanoda_lib 0da9f98(v0.4.32)です。

5.8ビルド後のソース不変確認 未実施

ビルドに使った 175,190 ファイルが原本と 1 バイトも違わないことを、保存してある SHA-256 一覧と再照合します(ビルド開始前の照合は一致済み)。

§7

この検証で言えること、言えないこと

すべての検査が通った場合に言えること

配布された Lean ソースが、指定どおりの Lean 4.33.1 と Mathlib v4.33.1 のもとでエラーなくコンパイルでき、主定理が標準の 3 公理だけに依存している、ということです。Lean のカーネルが正しく、Mathlib の riemannZeta などの定義が意図どおりである限り、これは Mathlib の RiemannHypothesis が証明されたことを意味します。

言えないこと

  • 証明の数学的な筋道が正しく理解できるか、既知の障害をどう越えているかは、この検証の対象外です。1,700 万行を人間が読んだわけではありません。
  • Lean のカーネル実装そのものの正しさは前提としています。別実装のカーネル(nanoda)による照合は準備済みですが、この時点ではまだ行っていません。
  • Mathlib 本体は公式のビルド済みキャッシュを使っています。ソースから再ビルドしてキャッシュと突き合わせる照合は、全検査の最後に予定しています。
  • 検証は 1 台の計算機、1 回の実行によるものです。
  • 配布元と著者については、PDF とサーバ応答から分かる範囲しか確認していません。
